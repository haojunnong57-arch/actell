# App 系统交互配对与 S3 连接

2026-10-06：当前 `feature/ncm-coredevice` 新增系统交互配对入口。参考 `app-only/SELF_CONTROL_ROUTES.md` 中 10 月 3 日的真实实验结果与当前 vendored idevice 的 responder API；没有复制带非商业限制的 StikPair 代码，没有读取或迁移旧 App 的私有凭据。

## 用户流程

1. 打开 NCM Probe，允许本地网络，点击「开始系统配对」。等待入口发布成功后，按 App 提示打开设置 → 隐私与安全性 → 开发者模式，选择 PhoneAgent NCM，完成设备密码确认和 PIN。App 收到协议 PIN 时显示它，不存储或日志输出 PIN。
2. App 自动保存当前配对身份。再次打开时保留已有身份，不要求导入 plist。旧实验 App 沙箱保持不变；这是本 App 的独立授权身份。
3. S3 连接 iPhone 原生 USB，确认 NCM IPv4 为 192.168.7.2/24。截图/点击按用户要求默认启用，不提供额外权限开关。App 启动或回到前台会自动连接已配对的 S3，也可点击「连接 S3」。App 自动从 S3 获取 IPv4 候选，无候选时尝试 IPv6；没有手动 greeting 前置步骤。
4. 使用 S3 NR1 转发依次完成 Pair Verify、动态隧道、TLS-PSK、RSD 和开发者服务检查。成功后可获取截图或向屏幕中心发送点击；点击回执只证明报告发送，实际效果由手机显示确认。
5. 「停止」撤销本地连接；控制连接进入后台自动关闭，配对期间持续后台任务允许用户切换设置。系统取消/过期时配对立即停止并保留已经保存的身份。

发现无候选时不会猜测端口或回退到手机自连接，界面明确报告缺少 RemotePairing 服务。普通 Lockdown 导入与 QueryType 位于独立高级诊断区，不承担系统授权流程。

## 实现边界

- 配对监听在 App 上，`_remotepairing-pairable-host._tcp` Bonjour 发布；系统主动连接 App。不是 S3 上的配对监听。后续控制连接只走 S3。此前 app-only 证明系统主动连接 App 的配对可行，而本机主动控制连接在认证前遭系统拒绝；S3 是否解决该限制仍需实机验证。
- 配对需要 iOS 26+ 的 BGContinuedProcessingTask。明确请求即时后台执行，不用静音音频、定位或 VPN。后台任务不能启动时显示重试状态，避免用户在没有监听时进入设置。
- Rust `ncm_pairing_start(1,…)` 是显式新配对 API，使用当前 responder 的 `accept_fallible`。两阶段事件分别返回经过 M5 签名验证的 provisional/committed 身份；Swift 原子写入并同步文件后才调用 `ncm_pairing_ack`，未获得持久化确认前禁止发送 M6。每阶段确认限时 10 秒；整体 180 秒；最多接收一个系统连接。
- 记录在本 App 的 Application Support/RemotePairing/identity.plist，使用 iOS 文件保护，排除备份。包含控制者私钥、手机长期公钥、配对标识、手机 UDID/model/altIRK。记录不会出现在报告或页面文本中。失败不会隐式新配对，也不会覆盖已有不同身份或降级已提交状态。
- provisional 记录保留：如果保存后断开，系统可能尚未接收 M6；文件存在不等于配对完成。先验证既有身份，失败时保留记录供后续恢复诊断，不自动删除或重配。
- Rust 队列事件释放时清零数据，Swift 明确清理临时 Data；不声称能消除 Swift 的所有值复制。禁止输出原始事件、plist、PIN、密钥与帧日志。
- 配对与普通 Lockdown/NL1 完全分开。`ios-app/PhoneAgent.xcodeproj` 的既有签名改动保留。

## 触控验证更新

用户回报系统配对完成、截图似乎可用，但中央点击无明显效果；这仍不等于已证实输入有效。

触控现在只启动屏幕视频会话，不请求音频流。当前已验证的 pymobiledevice3 `touch_session` 参考实现也使用视频会话打开触控授权条件。视频数据只在隧道内接收并丢弃，不解码、保存或播放。第一包有效视频到达后等待 350 ms 再连接 HID，让系统有时间匹配已授权触控服务；这只是针对首帧匹配时序的改进，不宣称已定位用户这次失败原因。

「验证点击实际效果」打开前台测试页，中央放置一个计数按钮。点击下方「经 S3 点击中央目标」只发送一次 normalized (32768,32768) 的按下/抬起；计数仅由界面真实按钮事件增加，不由发送回执修改。测试期间不要手动触碰中央目标。报告返回后再等 500 ms 给界面投递留出时间，显示计数是否变化。超时/取消关闭连接，不自动重发。

该验证证明当前测试页面是否实际接收触摸。中心空白处不响应、截图前后存在动画，均不能单独用来判断 HID 成功。普通控制接口仍返回「报告写入，视觉效果未验证」。


## 会话与测试页稳定性更新

用户澄清“S3 断开”是 App 的截图/点击按钮变灰，不是 USB 网卡消失。`ready=false` 会禁用操作按钮：冷启动尚未认证、进入后台关闭会话、协议操作失败均可触发；不能据此断言物理 NCM 断开。

- 移除「点击屏幕中心」这个没有可观察目标的独立按钮，仅保留有实际计数目标的验证页。
- 截图与触控授权在 App 连接配置中始终启用，移除两个默认关闭的开关；触控视频仍按实际操作启动，不读取音频。
- 测试页的 fullScreenCover 从动态 List Section 移到 NCMProbeView 的稳定根节点，禁止交互式手势关闭。成功/失败均保留计数及结果，只有用户点击关闭才正常退出。尚未通过真机复测证明这就是此前自动关闭的唯一原因。
- 前台已连接会话每 20 秒执行一次只读开发者模式/镜像检查，产生真实隧道流量，避免 S3 转发通道 60 秒空闲回收。保活与截图/触控共用操作门控，不并行请求、不产生输入，也不自动重发点击。
- 配对身份存在时，启动及返回前台自动验证连接。进入后台仍关闭控制会话（系统配对的持续后台任务除外）；协议错误仍关闭不可信会话，保留最近失败原因，页面提供重新连接入口。未修改 USB 断连或固件空闲回收规则。


## 视频准备失败与截图会话隔离

用户进一步报告按钮变灰之前显示「音视频流失败」。旧实现的 Session.start_touch_media 在任何启动失败时撤销整个 authenticated generation；Swift 也在每个操作失败时关闭 handle。这解释了视频失败之后截图按钮一同不可用的路径，但不意味着 App 退出或 USB 网卡断开。

新实现中，视频准备的 DisplayService/UDP/HID 连接由本次操作局部拥有；失败或取消后丢弃局部资源，不撤销已经认证的主隧道。ABI 新增事件 10 表示可恢复的 touch preparation failure（未发送任何触摸报告），Swift 保留 handle，App 保留 ready 和截图能力。阶段 13–18 分别区分视频接收端口、连接视频服务、请求视频会话、解析协商回复、等待有效视频包、连接触控服务。普通错误或触摸 Down/Up 发送结果不确定仍关闭会话，不自动重发输入。

回归：Rust backend 28 + vendor 175 个测试通过；含真实 Session 的视频准备失败/取消不撤销截图 generation 回归。Swift→ABI 合成所有权回归等 19 个 fixture 测试通过：视频准备超时后在同一 handle 上继续只读请求，之后模拟不确定触摸失败仍关闭 handle。clippy all-targets/offline-fixtures -D warnings 通过，签名真机构建通过。首次安装遇到 CoreDevice 4016（Mac 无法获取手机可安装开发连接）；用户恢复无线开发连接后重试，安装成功，已有配对身份保留。该安装错误与 App 内视频服务失败是不同连接路径；本轮修改的真实点击效果仍待手机复测。


## 取消额外 RTP 到达门槛

用户报告截图收到，而触控在「接收有效视频包」超时。本次排查确认：先收到符合 source port/SSRC/payload type 的 RTP 包，以及最近 2 秒持续收到包，都是本实现额外增加的门槛，不是此前真实触摸验证采用的 pymobiledevice3 touch_session 的条件。

现已取消等待首包与 2 秒包新鲜度要求。仍执行独立的 DisplayService 视频会话协商、保留会话、350 ms 系统触控服务匹配等待、再发送 HID Down/Up；不调用截图服务、不请求音频、不解码视频，后台接收的数据只丢弃。视频接收错误导致的实际通道失效仍阻止发送，视频协商失败仍不发送点击且保留截图连接。

这修复的是当前实现额外阻塞触控的条件，不声称完整绕过系统的媒体会话授权要求，也不声称新版本已证明触控成功。RTP 超时本身不能区分手机未发包、隧道未传包或过滤器不匹配；用户原反馈不足以确定其中哪一种。

本轮取消 RTP 门槛版本：Rust backend 27 + vendor 175 测试、Swift ABI chain 19 测试及 clippy 通过；签名构建、无线安装和启动成功。截图由用户确认收到，取消额外门槛后的触控结果仍待测试按钮计数验证。


## 当前手机端验收结果（用户回报）

2026-10-06，取消等待 RTP 包的门槛版本安装后，用户确认：点击「经 S3 点击中央目标」后「收到触摸」计数增加；「获取截图」显示实际截图。计数只由中央 SwiftUI Button 的 action 增加，发送回执不修改计数；截图由 ScreenCaptureService 的实际 PNG 请求返回。结合当前生产 App 强制 NCM 接口绑定、NR1 OPEN/TUNNEL 与 S3 主动连接手机的实现，这构成当前手机/固件组合的端到端截图与真实触摸成功证据（用户现场验证，非代理独立屏幕观测）。

架构仍是 App 生成协议请求并持有身份，ESP32-S3 通过 NCM 提供手机认可的外部连接来源及双向字节转发；截图和 HID 处理发生在 iPhone。不是 ESP32 单独持有配对身份或独立生成完整 CoreDevice 控制协议。尚未由本结果覆盖任意目标坐标、拖动/键盘、重启恢复、后台持续运行或长期稳定性。


## 主界面简化与保活不打断操作

按用户要求移除主界面的连接准备、NCM 诊断、普通 Lockdown 会话及最近结果区域；SDK/固件协议接口保留。主界面仅显示配对与连接状态、同一行「服务控制：连接/重新连接、停止」、截图、点击验证及收到的截图。截图和点击始终授权，不添加开关。

每 20 秒的前台保活此前设置了与用户操作共用的 `running`，导致 UI 定期禁用按钮、出现 ProgressView。这是维护请求状态被错误暴露到界面，不是定时刷新截图。现用独立的维护占用状态：保活不改变 UI 忙碌状态；用户请求排队等待正在进行的只读保活完成，再使用同一原生 handle 顺序执行。重新连接先取消并等待旧维护任务结束，避免旧请求抢占新连接。保活确实失败时仍撤销失效会话并显示未连接，不隐瞒真实断连。前台恢复自动连接保留。
